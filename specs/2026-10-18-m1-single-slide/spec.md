# 需求规格 · M1 单页生图展示链路

> 任务起始日期：2026-10-18。阶段 1～4 已完成，人类已确认方案全部三项。阶段 5 检查点 A～D 与步骤 9 已通过；独立素材已获人类确认，正式 v1 等待人类检查，最终重绘尚未执行。实际证据持续记录于 design.md。

## 一句话需求

从已确认的单页大纲和品牌视觉方向出发，生成可编辑 v1 PPT，完成中文文本自适应，再以该页画面、准确文案和背景/插画等素材为依据，通过 GPT 生图模型重新设计为协调、美观的整页展示图片，并核对内容与布局。

## 背景与目标

- 为什么做：用户认为现有命令行制作的 PPT 缺乏协调性和高级感，希望通过生图模型改善最终展示效果。
- 解决什么问题：让文字、品牌背景、插画和产品图片形成统一的视觉设计，同时保留可编辑 PPT 作为修改基础。
- 对应产品流水线环节：已确认大纲 → 品牌风格 → 背景/插画素材 → v1 组装与文本适配 → 生图整页重绘 → 检测与人工验收。
- 目标是验证上述能力，最终视觉质量由人类验收，不能以“已生成图片”代替质量通过。

## 四项必填

### 1. 做什么（功能行为）

- 先检索喜茶 2025 年年度营销相关资料，拟定主题文案和大纲，交人类确认后使用。
- M1 选取一张代表性内容页验证链路；具体页面主题随大纲确认，不预先锁定。
- 收集品牌主题颜色、文化元素和视觉特征，汇总为待确认的风格方向，再通过生图模型生成背景及所需插画。
- 组装 1 页可编辑 v1：文本可编辑；存在独立插画/图片时，保持可独立移动和缩放。布局根据内容选择，不强制固定为标题加正文。
- 所有中文文本使用 src/text_fit.py 适配。
- 将 v1 页面画面、准确文案和关联素材交给 GPT 生图模型，允许调整排版、配色和装饰，使整页协调统一。
- 生图结果必须完整保留已确认文字、数字和品牌名称，不允许擅自改写内容。
- 检测 v1 的文本布局，并核对最终展示图片的内容和视觉质量。

### 2. 为谁做（使用者与场景）

- 使用者：仓库维护者，先在本机验证。
- 典型场景：以“我是喜茶员工，汇报品牌 2025 年年度营销情况”为样例情境；不代表真实雇佣关系或内部数据访问权限。
- 使用频率：本阶段按单页技术链路验证，不承诺批量能力。

### 3. 关键业务规则

- 输入：经人类确认的单页大纲、准确文案、品牌风格方向，以及所需图片/生成素材。
- 输出：1 页可编辑 v1 PPT、最终生图展示 PNG、检测与视觉核对记录；辅助渲染文件按后续方案确定。
- 生图服务：用户原要求 GPT 的最先进生图模型；阶段 2 已明确首轮用当前会话生图工具验证效果，接受底层型号无法保证。未来需要明确指定型号时再确认 API 接入，不默认为本次范围。
- 文本下限：10pt；仍放不下时报告失败并请求精简，M1 不自动拆页，不无限缩字号。
- 视觉素材：AI 重新生成或采用可商用素材，登记来源；只从参考提取风格参数，不复制参考模板原图、插画或字体。
- 字体：仅用 fonts/README.md 白名单字体，测量、PPT 指定字体与辅助渲染字体一致。
- 整页生图可以调整视觉表达，但不得漏字、改字或更改已确认数字；出现此类问题不能通过验收。
- 失败处理：保留可编辑基础和已有产物，报告失败环节；修复最多 3 轮，仍未通过则停止并说明方案问题。
- 资料事实和图片来源必须可追溯；公开资料不足时列出缺口交人类确认，不自行编造经营数据。
- manifest 的用途已向用户解释：保存逐页元素、文字、位置/尺寸和素材关联，支撑后续改动识别。M1 是否实现及最小字段由阶段 4 方案提出并经人类确认，本阶段不视为已获范围确认。

### 4. 验收标准（可观察、可验证）

- [ ] 样例文案、大纲及品牌风格经人类确认，采用喜茶 2025 年年度营销汇报情境。
- [ ] 按确认的操作流程完成单页链路，脚本可运行、无未处理报错。
- [ ] v1 可用 python-pptx 重新打开，页数为 1，元素数符合后续确认的页面结构。
- [ ] v1 文字可编辑，图片/插画按结构要求作为独立元素保留；中文适配统一经过 src/text_fit.py。
- [ ] v1 几何检测无文字溢出、越界和非预期碰撞，检测结果可复核。
- [ ] GPT 生图模型生成整页展示 PNG；已确认文字、数字和品牌名称逐项核对一致。
- [ ] 人类对照大纲与风格方向，确认最终图片主题一致、图文协调、无明显突兀元素，视觉效果达到本次认可标准。
- [ ] 超量文本、渲染失败或生成内容不一致时明确报错/标记未通过，不交付为成功结果。

### 官方资料核实（已检索并打开页面）

- [GPT Image 2.5 Sunburst 模型页](https://developers.openai.com/api/docs/models/gpt-image-2.5-sunburst)：截至本次查询，官方列为最强生图与编辑模型，支持文本和图片输入。按用户“最先进”的要求，作为可明确指定型号时的首选验证对象；实际账号是否可调用尚未验证。
- [Image prompting](https://developers.openai.com/api/docs/guides/image-prompting)：支持以参考图编辑、明确保留内容并检查输出；质量优先时建议先验证 Sunburst。文档示例不能替代喜茶样页实测。
- [Image generation](https://developers.openai.com/api/docs/guides/image-generation)：支持图像生成/编辑、PNG 和透明背景；同时列明文字清晰度与位置、品牌一致性、精确构图仍有限制。因此不能承诺整页中文和数据一次生成完全正确。
- 当前会话 image_gen 工具支持参考图片编辑，但公开给本会话的参数没有 model 字段。不能仅凭工具存在宣称其实际使用 Sunburst 或可由本地脚本直接调用。

### 检测边界与需先开的 spike（均未执行）

1. 文本适配与辅助导出：批准验证方案后，以固定中文文本及同一套白名单字体验证 src/text_fit.py → 可编辑 v1 → PDF/PNG；检查断行、字体、页数、元素和几何结果。LibreOffice 仅承担参考页/检测载体导出，不承担最终美观目标。
2. 整页生图：将代表页画面、独立素材和完整逐项文案作为输入，使用选定接入路线，验证生图是否协调、文字/数字是否完整、PNG 与透明素材是否符合要求；记录输入输出、可获取的模型标识、参数与修复轮次，最多修复 3 轮。样例内容须先经人类确认。
3. 最终图片核对：测试逐条文案和数字核对流程，并用故意缺字/改数字的检查样本验证能否发现问题。OCR/视觉模型只能辅助，不能把自动识别成功当成绝对保真；保留人工逐项签核。若没有独立识别能力，明确记录人工核对，不称为自动检测。
4. 字体边界：v1 可以锁定白名单字体；整页生成图中的字形不能直接等同于该字体。需在设计阶段明确最终展示图的字体验收口径，不能虚称满足精确字体一致性。

## 代码勘察（阶段 3，2026-10-18）

### 现状理解

仓库处于规范与工具骨架阶段，还不是可端到端运行的 PPT skill。src/ 实际只有空的 __init__.py、模块说明 README.md 和 text_fit.py。唯一实现的业务能力是基于 Pillow 测量中文/混排文字、选择整数字号，并通过 python-pptx 文本框设置自动缩放兜底。大纲/风格文件只是 Markdown 填写模板，没有解析器、统一配置、PPT 组装、manifest、渲染或检测实现，也没有 CLI 或 SKILL.md 入口。先前的喜茶试图由会话生图工具直接生成，与 v1/文本适配尚未接通。M1 需要补齐数据输入、组装、辅助导出和几何检查，再由会话生图工具依据 v1 参考页及独立素材生成最终图片；本地 Python 不具备直接调用该会话工具的现有接口，不能把它写成虚构的 SDK 调用。

### 源码发现与关联风险（仅静态勘察，未执行功能复现）

1. text_fit.py 第 64～74 行：处理比整行宽的单位时，如果一个字符也装不下，k 可能保持 0，unit = unit[k:] 不消耗输入，循环可能无法结束。需要在 spike 中先复现，再在批准范围内修复；不把“已实测”的历史说明等同于覆盖全部边界。
2. fit_textframe 使用 cjk_wrap 的结果估计字号，但写入时仅按原文显式换行分段，没有写入测量出的所有折行；源码也没有设置 line_spacing/space_before/space_after。测量的 1.2 行高不保证等于实际引擎布局，须选明确的一致性策略并做 LO 验证。
3. 下限不足时 fit_textframe 返回 None，却仍写入 floor_pt 并保留自动缩放；若调用方忽略返回值，可能出现低于 10pt 的引擎缩放。builder 必须把 None 视为内容超量，不得静默保存成功成品。
4. v1 的图层含全幅背景，几何检查不能把全部矩形相交都判为碰撞；需要区分背景、允许叠放的装饰、文字安全区与图片主体。生图重排后原坐标不再适用，最终 PNG 单独核对。
5. 内置生图工具支持图像输入，但未验证 v1 页面的参考图编辑和品牌/文字保持；当前直接生成样图不能替代这个检查点。
