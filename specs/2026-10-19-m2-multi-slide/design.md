# 技术方案 · M2 五页可编辑 PPT

> 2026-10-19；分支 `feat/m2-multi-slide`。
> 阶段 3 影响范围已获人类确认。阶段 4 方案已于 2026-10-19 获批准，当前进入阶段 5。

## 先看实施后的结果

维护者将能用一份逐页大纲对应的执行文件，生成一套五页 PPT。文字可以直接修改，插画可以单独移动；每页都有自己的参考图和检查结果。程序会说明哪一页、哪个元素出了问题，任何一页失败都不会将整套判为通过。

本轮交付五页 v1、背景与透明插画、元素清单、辅助 PDF、五张参考图及检查记录。整体沿用已认可的暖白、茶绿与原创茶饮插画方向，通过不同版式组织不同内容。整页模型美化及图片展示版仍按后续路线推进。

建议确认本方案中的三项安排：

1. 新增 M2 入口和版本 2 输入，保留 M1 原有输入、命令及验收证据。
2. 先验证两页技术样例，再制作正式五页；任一页失败则整套失败。
3. 技术链路跑通后，检索并提交五页大纲、风格与素材安排供人类确认，再制作正式页面。

## 方案概述与边界

- 复用现有 Python、python-pptx、Pillow、PyMuPDF、LibreOffice、已登记思源黑体及中文适配模块，不安装新库或接入模型 API。
- 只扩展 `outline.py`、`builder.py`、`render.py`、`checks.py`，新增 `m2.py`；配套文件见下一节。
- M2 入口仅提供 `validate / build / check`。它不调用整页生图，也不识别人类修改后的 PPT 差异。
- 多版式通过逐页指定文本与图片框实现；本轮不实现自动布局引擎或 Markdown 通用解析器。
- 模式 B 内容仍由会话检索和共创，人工确认后的 Markdown 为阅读稿，JSON 为执行源。两者须逐页核对，不声称程序自动同步。
- 各页可使用大数字、原生文本底色块、图文分栏等现有能力；不新增原生复杂图表。资料不支持的数据不编造。

## 数据结构与接口

### 1. M2 执行输入

新增 `load_deck_outline(input_path)`，只接收 `schema_version=2`；旧 `load_outline(input_path)` 继续只接收版本 1 和一页。共用字段校验可在 `outline.py` 内抽小函数，不将 M1 的单页限制直接删除。

| 层级 | 字段与约束 |
|---|---|
| 整套 | `schema_version=2`、`deck_id`、`title`、`canvas`、`style`、`sources`、`slides`、`asset_source_record`；最后一项为素材来源记录的项目相对路径，正式样例指向本轮 source-record.json；执行源仍按 LF/CRLF 规范化计算哈希。 |
| 画布 | 全套统一 16:9；正式样例 960×540 pt，参考图宽 2560 px。仍接受既有参考宽度合法范围，不承诺模型图片固定像素。 |
| 字体 | 正式样例仅用已登记 `regular` / `bold` 思源黑体。沿用路径、家族名、字重和文件哈希配置；未登记字体不得进入正式素材/验收。程序校验配置与实际文件，授权白名单由登记与审查核对，不冒称能自动判断授权。 |
| 来源 | 每条有唯一非空 `id`、`publisher`、`date`、HTTP(S) `url`。实际事实核对由会话与人类完成，程序只校验结构与关联。 |
| 页面 | 必填 `slide_id`、`layout_type`、`notes`、`source_ids`、`texts`、`images`；notes 为字符串，可为空；`content_groups` 继续可选。页 ID 整套唯一，列表顺序就是页面顺序。 |
| 版式 | `layout_type` 为 `cover / columns / image-text / data / closing`，是说明与验收标签；不是自动生成坐标的模板系统。 |
| 文字与图 | 复用现有文本、颜色、边距、字号上下限、底色、对齐、图片框和透明要求；页内所有形状 ID 唯一，不同页允许同名形状。每页恰有一个标题文本和一张背景图。 |
| 来源关联 | `source_ids` 是无重复且指向全局来源的列表。非空时须有来源文本，且将对应完整链接写入本页备注；为空时不强制来源页脚。具体事实是否需要引用仍在大纲核对，不靠空列表跳过来源责任。 |

输入校验错误应包含页序、`slide_id` 与相关元素 ID；整套字段错误则明确指出字段。`check_assets(outline)` 扩展为遍历全部页，保留 M1 情况下原有错误标识；M2 错误加页面信息。

JSON 执行源不是只写五页的特制格式：技术验证允许两页，正式样例验收必须恰为五页；本轮不宣称已验证任意规模。`notes` 为人类讲稿，另拼接本页资料链接，不能上屏替代正文。

`source-record.json` 含版本和图片条目；每条保存项目相对路径、实际文件哈希、来源类型、工具/底层型号、实际尺寸/透明情况及对应生成提示词。复用条目另记原路径、原哈希和原生成记录位置；人类确认原话与状态仅在实际取得后记录，不因文件存在自动写为已批准。完整 validate/build/check 核对所用图片均有对应记录且文件哈希一致；schema-only 不要求未生成素材或来源记录已存在。内部脚本生成的测试夹具明确登记为 internal-test-fixture，只在 spike/regression 使用，不放入正式五页素材。

### 2. 元素清单与重开核对

新增 `build_deck(outline, config, out_root)` 构建 M2；原 `build_slide(...)` 继续限制单页并生成版本 1 清单。必要的复用在 `builder.py` 内完成，不额外建 manifest 模块。

M2 `manifest.json` 使用 `schema_version=2`，保留原有整套输入、PPT、画布、字体和运行标识字段，增加或扩展：

- `slides[]`：每页 `slide_id`、从 1 开始的 `slide_index`、`pptx_slide_id`、`layout_type`、`notes`、`source_ids`、本页来源、`content_groups` 与 `shapes`。
- `pptx_slide_id` 是库读出的 PPT 内部页面编号；已在本机安装的 `pptx/slide.py:224` 核对 `slide.slide_id` 属性。只将它作为当前运行内的读回证据，不当作跨重建不变的业务 ID。
- 形状记录继续包含页内 ID、原生 shape ID、层级、准确文字、实际折行、字体、几何、图片路径与哈希等；复合定位用页面 ID + 页内形状 ID。
- 素材来源记录文件的相对路径与 SHA256；其实际文件存在且覆盖本轮所用图片，由 M2 构建/检查核对。

`verify_reopened(pptx_path, manifest)` 接受版本 1/2 清单：按清单页数核对 PPT，再逐页核对顺序、元素、图片和文字。M2 另核对内部页面编号、备注及来源关联；版本 1 不追索新增字段，旧证据不迁移。

构建中遇到内容超量，错误定位到页面/元素，不生成“构建通过”结果。独立运行目录保留问题证据，只有成功保存并重开核对后才更新最新成功构建指针。

### 3. 辅助导出

新增 `render_deck_reference(pptx_path, config, run_dir, slide_records)`。由完整清单传入页面顺序与身份，内部一次 LO 转出整套 PDF，再遍历每页：

- 实际页数须等于清单页数，每页尺寸匹配统一画布。
- 各页保存为独立 `reference-01.png` 至 `reference-05.png`；技术样例按实际页数生成。
- 返回整套 PDF 路径/哈希，以及 `pages[]` 中每页的页序、业务 ID、参考图路径/哈希和实际像素；路径相对本次 run。
- 保留会话字体临时加载、独立 LO 配置目录、独立导出目录、超时与退出码处理。不读上次 PDF 冒充本次结果。

原 `render_reference(pptx_path, config, run_dir)` 保留单页约束，仍输出 `reference.png`、`reference_png`、`reference_sha256` 等原字段；它可以调用内部公共逻辑，但不改变 M1 CLI 与已验收生图交接所依赖的契约。45 秒转换超时先维持既有配置；若真实样例超时，按修复规则定位并回到方案，不直接假定是增加超时即可解决。

### 4. 逐页检查与汇总

保留 `audit_page(page, manifest, tolerance=1)` 的 M1 语义；新增明确接收某一页清单的 `audit_slide(page, slide_record, font_records, tolerance=1)`，供多页检查使用。二者复用相同的字形分配、字体、字号、有效文本区和碰撞检查。

新增 `check_deck_v1(pptx_path, pdf_path, manifest, config)`，先核对实际 PPT 与清单，再逐页核对 PDF：

- `slides[]` 返回各页身份、`passed`、元素数、文字结果、PDF 实际字体和问题。
- 问题至少含 `code`、`slide_index`、`slide_id`，有对应元素时附页内 ID；缺页等整套错误不能伪造正常页面结果。
- 整套 `passed` 只在所有页面、页数、对象、字体、内容和几何都通过时为真。页数不足直接失败，但仍输出完整结构的失败报告，不因缺少正常字段二次崩溃。
- 保留输入、PPT、PDF 哈希，视觉与人类确认状态初始为 pending；另由 M2 入口绑定逐页参考图和素材来源记录。

原 `check_v1(...)` 保留旧单页结果字段，旧 `audit_page(...)` 调用者无需改代码。文字检查只忽略换行/空白，不忽略数字、标点、单位或“近/超”。

### 5. M2 CLI 与运行证据

计划入口：`python -m src.m2 validate/build/check`，参数沿用 `--input`、`--out`、`--schema-only` 和 `check --soffice`。不在默认路径覆盖 M1 输出；M2 命令拒绝写入 M1 专用素材/产物目录。命令明确显示实际页数，正式五页验收另核对 5。

- `validate --schema-only`：校验结构与字体，`ready=false`，不能表述成可交付；完整 validate 另校验全部实际素材及来源记录。
- `build`：输出新 run 的 PPT、清单、各页元素数量及字号结果；记录 PPT/清单/输入/素材来源哈希。
- `check`：核对安全运行目录、输入、PPT、清单、字体和实际图片证据；再导出、逐页检查并写报告。显示人类可读的页级摘要，完整数据保存在 JSON。退出码 0 通过、2 内容/素材/证据错误或检查不通过、1 环境/执行失败。
- M2 内实现少量专用运行读取校验，复用现有路径、哈希和 JSON 工具，不直接把 M1 命令模块作为依赖，也不为此新增通用状态框架。
- 安全路径校验拒绝运行目录越界及 PPT 文件名越界；证据验证必须覆盖实际文件，不能只信 latest 中的布尔值。

状态为 `built → checking → awaiting_v1_confirmation / failed`。重新 check 前清除该运行的旧确认引用、旧检查摘要和参考图引用。证据改变或执行失败时返回失败；不得返回旧报告充当本次成功，能安全定位当前运行时将最新状态标为 failed。历史报告留在原运行中，不篡改旧证据。

来源记录变化须重新完整 validate/build/check；实际图片替换、字体变化、输入或 PPT 改变也须重新处理。手改 PPT 后本轮仍需人工同步执行源，再重建；自动 diff 留待 M3。

人类确认不由三个命令自动完成。实际确认后，会话在对应 run 保存 `v1-review.json`，绑定输入、PPT、清单、检查报告及逐页参考图哈希，记录逐页视觉结果与人类原话，再在 `review.md` 引用；这不新增 CLI 命令，也不把模型图验收状态沿用到 M2。
