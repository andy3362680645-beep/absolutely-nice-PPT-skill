# 06 · 知识蒸馏协议

> 每个任务合入后执行。目的不是写总结，而是把"这次学到的、下次还能用的"沉淀下来，让后续任务起步更准。
> 只保留跨任务可复用的结论，不记录过程流水账。

## 什么该入库

| 类型 | 落点 | 例子 |
|---|---|---|
| 已验证的坑与根因 | `knowledge/pitfalls.md` | 库自带 fit_text 对中文失效及根因 |
| 可复用方案骨架 | `knowledge/` 或模板 | 三道防线、manifest 结构、生图提示词模板 |
| 项目结构变化 | `knowledge/architecture.md` | 新增模块、入口、数据流变化 |
| 编码约定 | `knowledge/conventions.md` | 路径配置、命名、幂等规则 |
| 字体/授权事实 | `knowledge/fonts.md` | 字体搭配、授权类型、登记 |
| 一次性任务记录 | `specs/.../` | 具体需求与过程（不进知识库） |

## 蒸馏四问

1. 这次最容易被重复踩的坑是什么？根因是什么？
2. 审查中发现的问题，哪些是规则能预防的？规则写进哪份文件？
3. 有没有形成可复用的函数、模板、提示词、检查清单？
4. `architecture.md` 描述的现状是否还准确？

## 刷新规则

- 每条知识标注日期；过期或失效的标记或删除。
- 改代码的同时，相关知识条目必须同步更新（随 commit 一起提交）。
- 知识库给 AI 看，用祈使句、短条目、可直接执行。

## 输出格式

```
【知识蒸馏】
更新条目：
- knowledge/pitfalls.md：新增/更新 …（日期）
- knowledge/architecture.md：…
可复用资产：
- 模板/函数：…
```

人类确认后随收尾提交一起合入（可并入原任务 PR 或单独开 docs 分支）。
