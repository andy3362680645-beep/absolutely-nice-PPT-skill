# 踩坑记录（pitfalls）

> 每条：现象 → 根因 → 正确做法 → 验证日期。AI 编码前必读，避免重复踩坑。

## 1. python-pptx / power-pptx 的 fit_text() 对中文失效

- 现象：对中文文本调用 `fit_text()`，python-pptx 1.0.2 直接报 TypeError；power-pptx 2.13 不报错但只返回"放不下"，不给出正确断行。
- 根因：源码中断行逻辑用 `text.split()`，即按空格断词。中文没有空格，一整段被当成单个"超长单词"，无法在中间断开。
- 正确做法：中文一律走 `src/text_fit.py`（Pillow 逐字符测量 + 按字断行 + 二分字号 + 标点避头尾）。
- 验证日期：2026-10-18（本地实测）。

## 2. 行高不能用纯字形高度估算

- 现象：用 Pillow `getbbox` 测得的纯字形高度 × 行数，会低估实际行高，导致文字仍溢出。
- 正确做法：行高系数取字号的 1.2 倍（`line_factor=1.2`），实测与 LibreOffice 渲染吻合。
- 验证日期：2026-10-18。

## 3. 测量字体、渲染字体、PPT 字体名三处不一致则测量失效

- 现象：`text_fit.py` 用 A 字体测量，但系统/PPT 实际用 B 字体，算出的字号不匹配，仍可能溢出。
- 正确做法：测量用的字体文件、LibreOffice 可用的系统字体、PPT 中指定的字体名必须是同一套（见 fonts.md）。

## 4. 把丑 pptx 直接转图片，不会变美观

- 现象：期望"渲染成整页图片后达到命令行做不到的美观"，但直接 LibreOffice 转 pptx 得到的图，排版美观度没有提升。
- 根因：渲染只忠实呈现排版结果，python-pptx 对渐变、复杂版式、图文关系表达能力有限。
- 正确做法：LO 导出作为真实 v1 的辅助参考和几何/内容检查载体；用户确认后将原页、准确文字及独立素材交生图模型整页重绘，再逐项核对最终 PNG。HTML/CSS 可作为后续另行验证的选项，不是美化唯一条件。
- 验证日期：2026-10-19，已用实际 v1 参考页及独立素材完成首次正式模型重绘并目视核对 13 项文字；人类已确认本图视觉效果，不推断批量稳定成功率。

## 5. 无限缩字号不是解决内容超量的办法

- 现象：字号被压到很小仍硬塞，导致投影不可读。
- 正确做法：字号下限 10pt；`best_font_size` 返回 None 时，调用方必须精简文案或拆页，把问题反弹回内容阶段。

## 6. 外部平台链接抓取不可控

- 现象：小红书/抖音等平台有反爬、登录墙、服务条款限制。
- 正确做法：抓取先开 `spike/link-crawler` 验证；失败即降级为"用户上传截图"。不做绕过平台风控的尝试。

## 7. 微信公众号文章直接抓取被 robots 拦截

- 现象：常规抓取/浏览器打开微信公众号链接会遇到 robots 拦截或"环境异常"验证。
- 正确做法：仅作资料调研时，可尝试带微信内置浏览器 UA 的请求；自动化浏览器无法过验证。与本项目核心无关，仅记录。

## 8. 用户在 WPS 里手动改动后，必须与 manifest 比对

- 现象：无法知道用户改了哪一页、哪个元素。
- 正确做法：生成 v1 时同步输出 `manifest.json`（逐 shape 记录 id/文本/位置/尺寸/图片路径）；读回 v1 后做 diff。该能力正式开发前先做 `spike/pptx-diff`。

## 9. 插画不是独立元素就无法在 WPS 中拖动

- 现象：插画与背景合成一张图后，用户无法单独移动插画。
- 正确做法：插画必须输出为透明底独立 PNG，单独作为一个 picture shape 插入 v1。

## 10. 极窄文本框会使旧断行逻辑无法前进

- 现象：最小验证用子进程复现旧 `cjk_wrap` 在 2 秒内不能结束；单字宽于整行时反复尝试同一字符。
- 正确做法：不可前进时明确报错；字号搜索可继续尝试更小字号，最低字号仍放不下则返回 None。不能靠超时后假称成功。
- 验证：`specs/2026-10-18-m1-single-slide/spike_text_fit.py`；2026-10-18 复现，修复后边界检查通过。

## 11. 字体文件的英文家族名不等于本机 LO 可用别名

- 现象：本机思源静态字体文件显示英文名称，但 Windows 实际枚举家族为“思源黑体”；使用英文别名时 LO 发生替换。
- 正确做法：核实系统实际别名，并核对导出 PDF 的 SourceHanSansSC-Regular/Bold；不只检查字体文件存在。混合拉丁文本实测存在宽度差异，当前适配保留 10% 横向余量并显式写入换行、行距。
- 几何检查使用 PyMuPDF 字号高度字框，避免将整行字体度量框误当可见字符；仍需参考图目视检查，不无限扩大容差。
- 验证日期：2026-10-19，本机 M1 spike 与正式单页真实 LO 导出；不推断其他系统可用别名完全一致。
- 同日续作另一次导出：用户字体文件与注册记录存在、哈希一致，但当前 Windows 会话没有枚举出思源，LO 替换字体；在同会话用 AddFontResourceExW 加载原字体后可枚举且实际 PDF 恢复思源。render.py 已将此作为导出期间的临时资源加载，并释放本次增加的引用；不重复安装字体或修改注册表。重新实际导出通过，修复 1 轮。

## 12. 自动几何通过也可能出现句号单独成行

- 现象：正式 v1 初版未溢出，但末尾句号单独成行，部分语义词组跨行，视觉不自然。
- 正确做法：闭合标点无法并回上行时，将上行末尾字符或完整西文单词与其一起下移；大纲可显式设置语义换行。只调整布局空白，不改准确文案或统计限定词。
- 验证：新增标点边界 spike；正式页第一轮修复后重新 build/check，内容与几何通过，参考图未见孤立句号或“喜茶”“提交”拆行。
- 验证日期：2026-10-19。模型最终重绘还须重新逐字和目视核查。

## 13. 保留已验收状态前，必须重新核对实际证据

- 现象：阶段 6 在隔离副本删除最终图后，旧 prepare-image 仍返回 passed=true、state=accepted，且会重写原交接包。
- 正确做法：生成最终图后的复跑先核对交接、文案/提示词、最终原图、核对记录及绑定图像哈希的验收；全部一致只读复用。任一证据缺失或改变，返回失败并使当前运行失败，不自动沿用旧验收或重写历史证据。
- 验证：2026-10-19 第一轮修复后，缺图、改核对记录、改提示词、改准确文字、改交接包五类负例均被拒绝；正式 accepted 版本复跑不写任何证据文件，图像及状态哈希未变。

## 14. Git 换行转换会使原始输入哈希误报变化

- 现象：2026-10-19 合并后，Git 将 JSON 的 49 行 LF 检出为 CRLF；实际文案、布局与产物均未改变，但直接按文件字节算哈希导致 prepare-image 拒绝原已验收运行。
- 正确做法：执行源哈希计算前只将 CRLF 统一成 LF；不要修改 JSON 内容或替换已验收图，也不要忽略真正的内容变化。图片/PPTX 等二进制产物继续按原始字节核对。
- 验证：LF/CRLF 两份相同输入得到同一哈希并兼容既有验收；把日期摘要从 2025.11 改为 2025.12 会产生不同哈希并被旧运行拒绝。真实 validate/prepare-image 与 compileall 均通过；收尾第二轮修复，无视觉产物变化。
